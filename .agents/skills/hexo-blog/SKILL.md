# Hexo 博客写作

**核心原则**：所有字段都有默认值，默认最小化输出。用户明确提出的需求优先，修改对应字段，其余保持默认。

正文采用通俗、自然、口语化的表达方式，以科普和实际经验为主，不要过于强调技术细节。文章不仅要内容准确，还要具备良好的阅读体验和视觉层次。

## 执行前检查

开始修改仓库前，先完整读取本文件。涉及生成封面的实际文章，还要读取`.agents/skills/icode-api-image/SKILL.md`，按本文件的项目参数选择模型和尺寸，按图片skill的流程处理密钥、生成状态和重试。项目skill已指定模型或尺寸时，不要改用图片skill的通用默认值，也不要重复询问用户已由项目规则确定的参数。

写入Front Matter前，检查现有文章中实际使用的分类和标签。没有合适的既有值时，先征求用户同意，不要自行新增。保存文章前确认封面任务的必需条件均已满足；封面和正文图片引用必须使用同一张已存在的图片。

# 默认模板

```yaml
---
title: {标题}
date: {YYYY-MM-DD HH:mm:ss}
tags:
  - {默认最多 1 个}
categories:
  - {默认最多 1 个}
description: {默认最简洁的一句话，15-30字}
---
```

默认使用以上字段。实际写入仓库的新文章还需生成封面并添加`cover`；其余（top_img、keywords、comments等）仍不写，除非用户明确要求。仅输出Markdown草稿时不生成图片、不写入仓库。

# 默认值

- **title**：用户没给就根据主题提炼，要具体，避免宽泛标题。
  - 推荐：`深入理解JavaScript闭包`
  - 不推荐：`关于闭包`

- **date**：使用当前系统时间。

- **tags**：优先从现有文章使用过的标签中选择最贴切的，默认最多1个。

- **categories**：优先从现有文章使用过的分类中选择最贴切的，默认最多1个。

- **description**：一句话说清楚文章讲什么、解决什么，控制在15-30字。
  - 推荐：`从作用域链与内存模型讲清闭包的本质与用法。`
  - 不推荐：`本文主要介绍JavaScript闭包的相关知识。`

# 分类与标签

新建文章前，检查`source/_posts`现有文章Front Matter中使用过的`categories`和`tags`，尽量沿用语义最接近的现有值，并保持写法一致。

- 不要因为主题不同就自动创建新分类或新标签。
- 如果没有合适的现有值，确实需要新增，先向用户说明拟新增的分类或标签并征求明确同意。
- 用户提出一个尚不存在的分类或标签时，也先确认是否同意新增。
- 未获同意前，不要自行新增或用近似新名称替代。
- 可以先完成不依赖该决定的正文草稿。

# 参数覆盖

用户明确提到某个参数时，只修改对应字段，其余保持默认。

| 用户提到 | 处理方式 |
|---|---|
| 标题 | 使用用户给定标题 |
| 封面 / 背景图 | 添加`cover` |
| 描述 / 摘要 | 使用用户给定描述 |
| 标签 / 分类 | 若已存在则按用户指定使用；若不存在先征求同意 |
| 顶部图 | 添加`top_img` |
| 关键字 | 添加`keywords` |
| 关闭评论 | 添加`comments: false` |
| 日期 | 使用用户给定日期 |

# 封面生成与引用

实际创建并保存新博客文章时，正文定稿后默认调用本机`icode-api-image` skill生成一张与文章主题匹配的封面。用户明确指定已有封面路径、明确不需要封面或仅要求Markdown草稿时，按用户要求处理，不额外生图。

执行要求：

1. 根据文章主题编写生图提示词，使用适合博客封面的横向构图，避免画面中出现文字、水印或无关装饰。
2. 通过`icode-api-image` skill执行生成流程，固定使用`gpt-image-2.6`，并发送该模型可用的最高横向分辨率`3840x2160`（4K），不要改用其他模型、尺寸或比例。对应命令应先执行`--select-configuration --model gpt-image-2.6 --size 3840x2160`，再执行`--generate`。项目已固定参数，不要询问用户选择模型或尺寸。遵守图片skill关于密钥、失败重试及费用的要求；如果服务端不接受此配置，停止封面流程并报告，不自动降级。
3. 在图片配置中选择`3840x2160`作为请求尺寸。审核验收时不检查生成文件的实际像素尺寸，也不因返回尺寸与请求尺寸不同而判定封面不合格；不要将实际返回尺寸描述为已验证的`3840x2160`或原生4K。
4. 将生成文件保存到`source/img`，文件名使用文章slug加`-cover`，保留生成结果的实际扩展名。若同名文件已存在，使用不覆盖现有文件的唯一文件名。
5. 在Front Matter中添加与图片文件完全一致的`cover`路径，并在文章正文中插入同一张图。正文图片默认放在引言段之后、首个二级标题之前，使用标准Markdown语法，例如`![月球表面探测车](/img/article-cover.png)`。不要只设置Front Matter而漏掉正文图片，也不要让两处引用不同文件。
6. 构建前检查图片文件存在、Front Matter的`cover`路径与文件一致、正文Markdown图片引用与`cover`一致。构建后检查文章HTML的头图和正文`img`都指向该图片，且图片已复制到`public/img`。任一检查失败都先修复；图片生成或验证失败时，不写入失效引用、不提交、不推送、不部署，并向用户说明失败环节。

生图skill位于用户级目录`.agents/skills/icode-api-image`，本地凭据由该skill保存在仓库之外。不得把API key写入文章、项目文件、skill文档、命令示例或Git提交。

# 【】系列博客规则

当用户提到“【系列名】系列”的博客时，按以下规则生成Front Matter：

1. 标题固定为`持续学习【系列名】（第n期）`，其中`n`为该系列已有文章中的最大期数加1；如果没有找到同系列文章，则从1开始。
2. 生成前先检查`source/_posts`中已有文章的标题和文件内容，识别标题格式`持续学习【系列名】（第n期）`。
3. 只统计相同系列名的文章，不能把其他系列或正文中偶然出现的`【】`内容算进去。
4. 第1篇文章需要根据主题确定`tags`和`categories`。
5. 后续同系列文章必须完整复用该系列上一期（或已存在文章）的`tags`和`categories`，即使本期主题不同或用户再次指定标签、分类，也不能改写系列已有值。
6. 系列规则只影响标题、期数、`tags`和`categories`；`date`、`description`以及用户明确指定的其他字段仍按通用规则处理。

例如，用户说“写一篇【Python】系列的博客”，若已有`持续学习【Python】（第2期）`，新文章标题应为`持续学习【Python】（第3期）`，并沿用该系列已有文章的`tags`和`categories`。

如果没有同系列文章，则标题为`持续学习【Python】（第1期）`。

# 正文写作规范

## 1. 文章结构

默认采用以下结构：

1. **引言**：从实际背景、现实问题或读者关心的现象切入。
2. **主体**：设置2-4个主要章节，每节有明确的核心观点和实质内容。
3. **总结**：回到文章主题，提炼核心结论或给出实际建议。

具体要求：

- 正文默认800-2000字，根据主题复杂度灵活调整。
- 不为凑字数重复表达。
- 每个章节都应提供新的信息、观点、案例或实际经验。
- 保证文章逻辑连贯，章节之间有自然过渡。
- 避免只有标题、没有实质内容的空壳章节。
- 不要为了追求章节数量而拆分本来连贯的内容。

## 2. 语言风格

- 语气偏口语化，像在跟同事交流，不端着，不写教科书腔。
- 多写实际经验、应用场景和具体案例。
- 讲原理要说明因果关系，讲用法要提供可以直接使用的示例。
- 语言直接，不堆砌修饰词。
- 尽量使用短句，避免复杂冗长的表达。
- 避免机械化的AI写作表达和模板化过渡语。
- 不要频繁使用「首先、其次、最后」「综上所述」等固定连接词。
- 不编造个人经历、实验数据、案例和引用来源。
- 对不确定的事实应明确说明，不要将推测写成结论。

## 3. 内容质量

- 优先回答读者真正关心的问题。
- 重要观点应有解释、论据或案例支撑。
- 技术文章应注意概念准确性，不能为了通俗而牺牲准确性。
- 行业分析应区分事实、观点和推测。
- 工具测评应尽可能体现真实使用场景和优缺点。
- 不要简单罗列网络上常见的信息，应当有自己的分析和总结。
- 文章应有明确的核心观点，而不是简单拼接多个知识点。

# 视觉排版与阅读体验

**核心原则**：采用主流优质博客的排版风格，参考Medium、少数派、微信公众号和掘金的优秀文章。

整体风格为：简洁、专业、清晰、有层次。

排版应服务于内容，不为了视觉效果堆砌格式。让读者能够快速浏览文章结构，也能舒适地阅读完整内容。

## 1. 标题层级

- 文章正文从`##`开始，只使用`##`和`###`，不跳级。
- `##`用于主要章节，`###`用于章节内部的小主题。
- 主标题应具体、有信息量，体现文章核心观点或解决的问题。
- 小标题尽量使用观点式表达，而不是简单使用「介绍」「分析」「总结」等宽泛词语。
- 标题应简洁，避免过长。
- 不要在每个标题中重复文章主题。
- 不要使用过多层级，避免文章结构过于复杂。

推荐：

```markdown
## 为什么AI时代更需要独立思考

### 工具降低了执行成本

### 判断力决定最终结果
```

不推荐：

```markdown
## 第一部分

### 第一部分的介绍

#### 第一部分的详细介绍
```

## 2. 段落与留白

- 每段控制在2-4句话，原则上不超过5行。
- 一个段落只表达一个核心意思。
- 段落之间保留一个空行。
- 长篇解释应拆分为多个自然段，避免出现大段文字墙。
- 不要为了缩短段落而将一句完整的话拆成多个段落。
- 章节之间保持适当留白。
- 不要连续堆叠标题、列表和引用块。

**目标：让文章在电脑端和手机端都具有良好的阅读体验。**

## 3. 重点内容与加粗

合理使用Markdown加粗，突出最值得读者记住的信息。

适合加粗的内容：

- 核心观点。
- 重要结论。
- 关键术语首次出现的位置。
- 对比关系中的关键词。
- 具有独立价值的总结句。

使用规范：

- 每个主要章节可以有1-2处重点加粗。
- 不要整段加粗。
- 不要连续多句话全部加粗。
- 不要将普通描述、过渡句和背景信息加粗。
- 同一术语后续出现时，不必反复加粗。
- 加粗应有选择性，避免整篇文章视觉上没有重点。

## 4. 引用块

使用Markdown引用块`>`突出具有独立价值的内容。

适合使用引用块的场景：

- 文章核心观点或具有启发性的金句。
- 重要定义、原则和结论。
- 值得读者停下来思考的观点。
- 具有代表性的原话或引用内容。

使用规范：

- 每篇文章通常使用1-3个引用块。
- 引用内容应简洁，最好控制在1-3句话。
- 引用块必须有实际内容价值。
- 不要把普通段落全部转换成引用块。
- 引用他人的原话时，应注明来源。
- 不得将改写内容伪装成直接引用。

示例：

```markdown
> AI可以帮助我们更快地得到答案，但真正决定答案是否值得采用的，依然是人的判断力。
```

## 5. 列表与表格

**列表：**

- 并列观点、操作步骤、注意事项和多个特征，优先使用列表。
- 有明确先后顺序的流程使用有序列表。
- 每个列表项尽量简洁。
- 列表前应有一句自然的引导语。
- 不要将本来连贯的叙述强行拆成列表。
- 避免过多层级嵌套。

**表格：**

- 适合展示对比、参数、优缺点和分类信息。
- 表格内容应简洁，避免放入大段解释。
- 只有存在明确对比关系时才使用表格。
- 不要为了排版好看而将普通段落转换成表格。
- 手机端阅读时应考虑表格宽度，避免列数过多。

## 6. 视觉分隔与辅助元素

- 使用`---`分隔文章主体与结尾，或用于少数具有明确结构边界的场景。
- 不要在每个章节之间都添加分割线。
- 适当使用行内代码标记技术名词、命令、文件路径和配置项。
- 代码块必须指定语言类型。
- 代码块前后应有简短说明。
- Emoji默认不使用，除非内容确实需要，且应保持克制。
- 不要使用大量装饰符号、重复标点或花哨的字符组合。
- 不要为了视觉效果添加无意义的空行。
- 不要使用不兼容标准Markdown的HTML装饰元素，除非用户明确要求。

## 7. 开篇与结尾设计

**开篇：**

- 第一段尽量从实际场景、现实问题或读者关心的现象切入。
- 可以使用一个值得思考的问题引出文章主题。
- 尽快说明文章要讨论什么。
- 避免冗长的背景铺垫。
- 不要使用「随着时代的发展」「在当今社会」等泛化套话作为固定开头。
- 不要在开篇就把全文所有结论全部说完。

**结尾：**

- 回到文章最初提出的问题或核心观点。
- 提炼1-2个值得读者记住的结论。
- 可以适当升华观点，但必须建立在正文论证之上。
- 不要机械地重复全文。
- 不要使用固定模板式结束语。
- 可以用一句有记忆点的话作为文章收尾。

## 8. 不同文章类型的排版策略

根据文章内容自动调整排版，不要所有文章都使用同一套格式。

| 文章类型 | 排版重点 |
|---|---|
| 技术教程 | 步骤清晰、代码示例、原理解释、常见问题 |
| AI与科技观察 | 观点突出、背景分析、案例说明、趋势判断 |
| 职场与个人成长 | 场景引入、观点分节、实际经验、结论提炼 |
| 产品与工具测评 | 产品介绍、功能对比、使用体验、优缺点 |
| 行业分析 | 数据与事实、逻辑推演、对比分析、结论 |
| 学习笔记 | 概念解释、知识结构、示例说明、实践总结 |

不要为了套用排版模板而改变文章本身的逻辑。

## 9. 排版质量检查

文章生成后，自动检查以下问题：

- [ ] 标题是否能够准确表达文章主题？
- [ ] 章节结构是否清晰，逻辑是否连贯？
- [ ] 是否存在过长段落或文字墙？
- [ ] 加粗是否突出真正重要的观点？
- [ ] 引用块是否有实际价值，是否使用过度？
- [ ] 列表和表格是否使用得当？
- [ ] 是否存在过多分割线、Emoji或装饰符号？
- [ ] 开篇是否能够吸引读者继续阅读？
- [ ] 结尾是否形成完整的观点闭环？
- [ ] 整体阅读体验是否简洁、自然、舒适？

**最终标准**：文章应当具有专业博客的视觉层次，同时保持自然的文字阅读体验。不要为了追求排版效果而牺牲内容质量。

# 中英文及Markdown格式规范

- 中英文之间不加空格。
- 写`JavaScript闭包`，不写`JavaScript 闭包`。
- 写`用let即可`，不写`用 let 即可`。
- 中文标点和英文代码、变量名之间保持自然。
- 代码、命令、文件路径和配置项使用反引号。
- 使用标准Markdown语法，确保Hexo能够正常解析。
- 列表使用`-`或`1.`。
- 不要混用多种Markdown格式表达同一层级的信息。

# 写完后的推送与部署

用户要求写一篇新文章时，默认完成文章文件、推送源码并部署。

源码分支和Hexo部署分支必须分开管理。`npm run deploy`会根据`_config.yml`中的`deploy.branch`把生成后的静态文件推到部署分支；这个分支可能被Hexo部署流程重写，不能用来保存源码提交。源码提交必须先推送到当前源码分支对应的远端分支，并在部署完成后再次核对该远端分支仍指向本次提交。

如果用户明确只要Markdown草稿或明确不发布，则只输出完整Markdown，不写入仓库、不推送、不部署。

## 1. 检查现有文章

- 检查`source/_posts`目录下的现有文章。
- 检查已有文章的Front Matter。
- 确认分类和标签均为现有值，或已经取得用户新增同意。
- 如果涉及系列文章，按照系列规则确定标题、期数和分类标签。
- 确认新文章封面已保存到`source/img`，且Front Matter的`cover`路径与图片文件一致。

## 2. 创建文章

- 将文章保存到`source/_posts`。
- 文件名使用清晰、稳定的文章标题。
- 文件名使用合适的英文Slug或拼音，避免特殊字符造成路径问题。
- Front Matter严格遵守默认模板和用户指定参数。
- 按“封面生成与引用”规则生成并添加`cover`；除封面外，不要擅自增加未要求的字段。
- 写入后检查Markdown格式和Front Matter是否正确。

## 3. 构建检查

运行：

```bash
npm run build
```

检查Hexo是否能够成功生成站点。

- 如果构建失败，先检查是否由本次文章导致。
- 修复本次文章导致的问题后重新构建。
- 不要带着构建失败的结果发布。
- 不要擅自修改与本次文章无关的项目配置。

## 4. Git提交与推送

执行前检查：

```bash
git status
git branch --show-current
git branch -vv
git fetch origin
```

确认：

- 当前分支是专用源码分支，不能等于`_config.yml`中的部署分支（通常是`main`）。
- 当前分支的远端目标是同名源码分支，不能把源码提交直接推到部署分支。
- 工作区和暂存区的已有修改情况。
- 本次提交不会包含其他已有或已暂存的改动。
- 不要直接相信`@{upstream}`：先比较当前分支名、上游分支名和`deploy.branch`，防止工作分支错误跟踪部署分支。
- 检查`git log --oneline HEAD --not origin/当前源码分支`，确认待推送范围，并说明其中已有提交是否属于本次源码分支。

如果当前分支没有同名远端分支，或错误跟踪了部署分支，使用当前分支名显式建立源码上游，不要改推`main`：

```bash
git push -u origin HEAD:refs/heads/当前源码分支
```

该命令只用于建立或更新源码分支；源码分支禁止使用`git push --force`。如果同名远端分支已经存在且发生分叉，先停止并处理分支关系，不要覆盖远端历史。

只暂存本次新增文章：

```bash
git add source/_posts/文章文件名.md source/img/本次生成的封面文件
```

若本次没有新生成封面（例如用户明确使用已有图片），只暂存文章文件。不要暂存`source/img`中的其他文件。

再次检查暂存区：

```bash
git diff --cached --name-only
```

确认暂存区只有本次新增文章和它对应的新封面后，再提交：

```bash
git commit -m "Add: 文章标题"
```

提交后，显式推送到同名源码分支，不使用可能指向部署分支的默认上游：

```bash
git push origin HEAD:refs/heads/当前源码分支
git ls-remote origin refs/heads/当前源码分支
git rev-parse HEAD
```

确认`git ls-remote`返回的源码分支哈希与`git rev-parse HEAD`完全一致后，才能进入部署步骤。不要用部署分支的提交历史判断源码是否已经推送；必要时用`git ls-tree -r origin/当前源码分支 source/_posts source/img`确认源码文件存在。

如果源码推送失败、远端分支哈希不一致、当前分支错误跟踪部署分支，停止部署，保留本次独立提交，并说明分支及提交范围问题。不要照抄Git提示改推其他refspec，也不要把源码分支强行推到部署分支。

如果无法将本次文章单独提交，先停止并说明原因，不要覆盖用户已有修改。

## 5. 部署

推送成功后运行：

```bash
npm run deploy
```

部署到`_config.yml`中配置的GitHub Pages仓库和分支。

部署完成后再次执行：

```bash
git fetch origin
git rev-parse HEAD
git ls-remote origin refs/heads/当前源码分支
```

确认源码分支仍指向本次源码提交，再分别报告源码推送和Hexo部署结果。部署分支只验证生成站点，不作为源码提交的保存位置。

## 6. 异常处理

如果出现以下情况：

- 当前分支等于部署分支，或错误跟踪部署分支。
- 源码分支没有可用远端上游，或源码分支发生分叉。
- Git推送失败。
- 源码分支推送后远端哈希无法与本地提交一致。
- Hexo构建失败。
- 网站部署失败。
- 存在无法安全隔离的用户修改。

不要擅自改推其他分支，不要反复执行可能造成外部变更的命令。

保留文章和当前提交状态，说明具体失败环节及结果。

不要在没有实际执行成功的情况下声称已经推送或部署。

## 7. 工作区未跟踪文件（绿色`U`）

开始和结束时都检查完整状态：

```bash
git status --short --untracked-files=all
```

`.gitignore`只忽略构建产物、部署临时目录和本机专用文件，例如`public/`、`.deploy_git/`、`node_modules/`、`db.json`、日志文件以及`.agents/skills/icode-api-image/`。不要用宽泛规则忽略`source/_posts/`、`source/img/`、`_config*.yml`、`package*.json`、`scaffolds/`或`themes/`，这些是源码的一部分。

如果源码工作区首次从部署分支恢复，发现大量合法项目文件显示为`??`，先逐项检查并建立一次源码基线提交；不得直接删除，也不得为了消除标记把整个`source/`加入忽略。基线提交后，文章任务只暂存本次文章和对应封面，结束时应确认没有本次产生的未跟踪源码文件。对于无法判断归属的文件，保留并报告，不要擅自删除。

## 什么是闭包

说人话就是：一个函数能记住它出生时的环境，哪怕这个环境所在的函数早就执行完了，它依然能读取里面的变量。这种能力就是闭包。

```js
function outer() {
  const msg = 'hello'
  return () => console.log(msg)
}

outer()() // hello
```

`outer()`已经执行完了，但返回的内层函数还能打印出`msg`，这就是闭包在起作用。

## 为什么能成立

JavaScript采用词法作用域，作用域在函数定义时就确定了，跟函数在哪里调用没有关系。

所以当函数被返回并保存下来，它引用的那层作用域链不会跟着外层函数一起销毁。引擎会把仍然需要访问的变量保留在内存中。

这也是闭包经常和内存管理一起讨论的原因。

## 常见用法

实际写业务时，闭包经常出现在以下场景：

- **数据私有化**：把变量藏起来，只暴露操作接口。
- **函数工厂**：批量生成带有不同预设参数的函数。
- **防抖节流**：使用闭包保存定时器或上次执行时间。

下面是一个简单的防抖函数：

```js
function debounce(fn, delay) {
  let timer = null

  return (...args) => {
    clearTimeout(timer)
    timer = setTimeout(() => fn(...args), delay)
  }
}
```

这里的`timer`被内层函数引用着，多次调用共享同一份状态，因此防抖才能生效。

## 一个常见的坑

老代码中经常会在循环里使用`var`声明变量，再创建闭包，结果所有闭包可能拿到的是同一个变量。

换成`let`就能解决这个问题，因为`let`在每次循环迭代中都会创建新的绑定。

## 总结

闭包的本质就是函数加上它定义时的词法环境。

理解闭包，不仅能帮助我们写出更灵活的代码，也能让我们更好地理解JavaScript的作用域、内存管理和函数式编程。
