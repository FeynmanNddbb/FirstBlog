最新开源大语言模型-千问、DeepSeek与智谱横向对比

最新开源大语言模型：千问、DeepSeek 与智谱横向对比

今天不再只介绍一个模型，而是把目前开源生态中最值得关注的三条路线放在一起比较：通义千问（Qwen）、DeepSeek，以及智谱（GLM）。三者都提供了不同规模的开放权重，但技术路线、推理能力、部署门槛和适合的业务场景并不相同。

需要先说明的是，模型版本迭代非常快，参数、上下文长度、许可证和 benchmark 结果可能随权重更新而变化。下表采用公开模型卡中具有代表性的版本做工程层面的整理，正式部署时应以对应版本的官方文档为准。

模型路线 代表版本 架构与参数特征 主要优势 部署印象
通义千问 Qwen3-235B-A22B、Qwen3-30B-A3B MoE；235B 总参数、约 22B 激活；同时覆盖大模型和轻量模型 中英文、多语言、代码、工具调用和可控思考能力较均衡 大模型版本需要多卡；30B-A3B 更适合开发者实验
DeepSeek DeepSeek-V3.1 MoE；约 671B 总参数、约 37B 激活；采用 MLA 等长上下文优化思路 数学、代码、复杂推理和中文任务表现突出 总权重规模很大，服务化部署对多卡互联要求高
智谱 GLM GLM-4.5 系列 面向推理、代码和 Agent 场景的混合模型路线；不同尺寸版本差异较大 中文交互、工具使用、智能体流程和企业场景适配较好 应按具体权重选择显存规格，不能用系列名称代替模型卡

一、三类模型的参数与架构比较

1. 千问：尺寸覆盖最完整

Qwen3 的特点是模型尺寸覆盖范围较宽，从适合本地运行的小型模型，到需要数据中心 GPU 的 MoE 大模型都有对应版本。以 Qwen3-235B-A22B 为例，模型总参数约 235B，但单次推理激活参数约 22B；Qwen3-30B-A3B 则进一步降低了激活规模，适合个人开发、边缘服务和低成本实验。

千问路线的工程优势并不只在参数量，而在于生态完整：模型权重、量化版本、推理框架、Embedding、重排序模型和多语言资料比较齐全。对于需要同时做中文问答、代码生成、结构化输出和工具调用的团队，Qwen 往往比较容易形成完整技术栈。

2. DeepSeek：用大容量 MoE 换取推理上限

DeepSeek-V3.1 采用大规模稀疏 MoE 架构，总参数约 671B、激活参数约 37B。总参数决定权重文件和部署门槛，激活参数则更多影响单 token 的计算量。两者不能混为一谈：虽然每次只激活部分专家，但服务端仍需要管理大量专家权重、路由计算和跨卡通信。

DeepSeek 的优势更集中在复杂推理、数学、代码和长链路任务上。它适合作为高质量主模型，尤其适合需要多步骤分析、复杂代码修改或专业方案解释的场景；但如果业务主要是简单分类、短文本抽取或高并发问答，使用如此大规模的模型未必经济。

3. 智谱 GLM：更强调中文产品化与 Agent

智谱 GLM 系列长期重视中文交互、工具调用、代码能力和企业应用。以 GLM-4.5 代表版本为例，公开资料通常会重点展示其推理、代码和 Agent 能力，但具体参数规模、激活规模、上下文上限和量化版本需要以实际模型卡为准。

与其把 GLM 简单理解为“又一个聊天模型”，不如把它看作偏产品化和智能体编排的一条路线。对于中文办公、知识库问答、流程自动化、浏览器操作和工具调用等应用，需要重点测试模型是否能稳定地产生工具参数、处理工具返回结果并在失败后继续执行，而不能只看静态问答分数。

二、关键参数横向对比

对比项目 Qwen3-235B-A22B DeepSeek-V3.1 GLM-4.5 系列
总参数规模 约 235B 约 671B 以具体版本模型卡为准
激活参数规模 约 22B 约 37B 以具体版本模型卡为准
模型类型 MoE MoE 系列内可能包含不同架构与尺寸
上下文能力 面向长上下文设计 代表版本最高约 128K，需核对具体权重 以部署版本和推理框架支持为准
推理模式 支持思考与非思考模式切换 适合复杂推理和代码任务 偏重推理、工具调用与 Agent
中文能力 强，兼顾多语言 强，中文和技术任务表现突出 中文交互与国内业务适配较好
轻量版本 较丰富，如 30B-A3B 轻量蒸馏模型生态较活跃 需要按具体系列选择
典型门槛 大模型多卡，小模型可本地实验 大模型多卡部署门槛最高 取决于具体权重规模

这里最值得注意的是“上下文长度”这个指标。上下文上限只是模型理论上可以接受的输入长度，不等于在该长度下仍然具备相同的检索准确率，也不等于服务端可以低成本支持高并发。实际系统需要同时测量长文档召回、关键信息定位、KV Cache 占用和首 token 延迟。

三、推荐推理配置

1. 通用 Transformers 配置

三类模型的加载方式通常都可以遵循 Transformers 的基本模式，但模型仓库名称、chat template、思考模式开关和特殊生成参数必须按照具体模型卡调整：

切换到 DeepSeek 或 GLM 时，不应只修改 model_name 就直接上线。应重新确认 tokenizer、模板格式、是否需要启用 thinking、停止词、工具调用协议和量化权重兼容性。

2. 服务化部署配置

如果使用 vLLM、SGLang 或其他 OpenAI 兼容推理框架，建议先用如下思路进行压测：

配置项 初始建议 对比时要观察的指标
dtype 优先 BF16；显存不足时测试 FP8/INT8 质量损失、显存和吞吐
max-model-len 先从 8K 或 16K 开始 长文本准确率与 KV Cache
tensor-parallel-size 按 GPU 数量和显存切分 跨卡通信、吞吐和稳定性
gpu-memory-utilization 0.85～0.92 起步 OOM 风险与并发能力
max-num-seqs 从低并发逐步增加 P50/P95 延迟和 tokens/s
量化格式 选择框架原生支持的版本 输出质量、加载速度和算子覆盖

对于 MoE 模型，不能只依据激活参数估算显存。专家权重是否全部常驻、专家并行方式、跨卡互联、KV Cache 类型和并发请求都会改变最终资源需求。

四、性能表现：不要只看榜单分数

1. 通用问答与中文表达

Qwen 和 GLM 在中文对话、办公文本和国内业务语境方面通常具有较好的可用性；DeepSeek 在技术问答、复杂分析和专业内容解释方面也很有竞争力。真正的差异往往出现在细节：是否理解业务术语、是否遵守格式、是否会过度扩写，以及在信息不足时能否明确说明不确定性。

2. 数学与复杂推理

DeepSeek 和 Qwen 的高端推理版本更适合多步骤数学、代码分析和复杂规划任务。GLM 也适合推理型 Agent，但应重点测试它在工具调用链中的稳定性。数学任务不能只比较最终答案，还要测试公式、单位、边界条件和中间结论；涉及精确计算时，应该让模型调用 Python、计算器或业务算法进行验证。

3. 代码生成与软件工程

三类模型都可以完成代码补全、接口生成、错误解释和重构，但工程质量取决于上下文和验证闭环。建议用真实仓库建立评测集，至少包括：

  • 能否读懂现有目录结构；
  • 能否遵循已有命名和代码风格；
  • 能否正确修改多个关联文件；
  • 是否会破坏原有 API；
  • 是否主动补充测试；
  • 编译和测试失败后能否根据日志修复。

“能生成代码”只是第一步，“能在真实项目中通过测试”才是更有价值的性能指标。

4. Agent 与工具调用

如果应用需要数据库查询、搜索、计算、文件处理或业务系统操作，建议单独建立 Agent 评测集：

测试项目 关注问题
工具选择 是否选择正确工具，是否出现无意义调用
参数生成 字段类型、必填参数和枚举值是否正确
过程控制 能否根据工具结果决定下一步动作
异常恢复 工具超时或失败后是否重试、降级或说明原因
结果表达 是否区分模型推测与工具返回的事实
安全边界 是否执行越权操作或泄露敏感信息

从这个角度看，Agent 性能不是单一模型能力，而是模型、提示词、工具定义、权限系统、错误处理和观测系统共同作用的结果。

五、按场景选择模型

业务场景 优先考虑 选择理由
中文知识库与办公助手 Qwen 或 GLM 中文表达、部署生态和业务适配较均衡
数学、代码和复杂分析 DeepSeek 或 Qwen 高端版本 更适合长步骤推理与技术任务
低成本本地部署 Qwen 小尺寸模型、蒸馏模型 显存和并发门槛更低
工具调用与流程自动化 GLM、Qwen、DeepSeek 均需实测 关键是工具协议和失败恢复能力
高并发短问答 小尺寸 Qwen 或蒸馏模型 不应让超大模型承担简单任务
智能配煤等工业场景 专业算法 + 任一模型作为交互层 模型负责解释和编排，数值结果由算法校验

六、我的思考：参数越大，不代表系统越好

第一，模型选择应该服从任务，而不是服从名气。如果任务只是分类、抽取和固定模板生成，参数更大的模型可能只会带来更高成本和更长延迟。真正应该比较的是单位成本下的任务完成率。

第二，开源的价值不只是免费。开放权重带来了私有化部署、数据可控、可审计和二次微调的可能，但同时也把 GPU、运维、量化、监控和安全责任交给了使用者。没有工程能力支撑时，开源模型不一定比 API 更便宜。

第三，MoE 解决的是计算效率问题，不是所有部署问题。激活参数较少可以降低单 token 计算量，但总权重、通信和并发下的缓存仍然可能成为瓶颈。部署前必须进行真实压测，不能只看参数表。

第四，benchmark 不能替代业务评测。公开榜单适合观察模型的大致能力，但不能回答“它能否正确完成我的任务”。建议使用真实脱敏数据构造测试集，分别记录准确率、引用正确率、幻觉率、首 token 延迟、生成速度、并发吞吐、显存和成本。

第五，大模型不应替代确定性算法。在智能配煤、金融计算、工业控制等场景中，语言模型适合做自然语言入口、方案解释、数据审计和流程编排；约束计算、指标预测和最终决策仍应由专业模型、优化算法和规则系统负责。

七、建议的模型评测表

指标 测试方法 结果用途
任务准确率 使用固定业务测试集 判断是否满足业务下限
格式合规率 校验 JSON、字段和枚举 判断能否接入自动化流程
幻觉率 对无答案问题进行测试 判断知识库和拒答策略
长文本召回率 在不同位置插入关键事实 判断上下文利用能力
首 token 延迟 记录 P50/P95 判断交互体验
生成吞吐 统计 tokens/s 判断服务容量
并发稳定性 逐步提高并发请求 判断生产部署上限
单请求成本 结合 GPU 折旧和电费 判断商业可行性

八、总结

通义千问、DeepSeek 和智谱 GLM 并不存在绝对的“第一名”。Qwen 的优势是尺寸覆盖和生态完整，DeepSeek 的优势是大规模 MoE 与复杂推理能力，GLM 的优势则更偏向中文产品化、工具调用和 Agent 场景。

如果是个人学习，可以从 Qwen 小尺寸模型或量化版本开始；如果追求复杂代码和推理质量，可以重点评估 DeepSeek；如果要做中文企业助手和流程自动化，则应把 GLM 纳入工具调用和 Agent 对比测试。更成熟的架构不是只部署一个模型，而是根据任务难度进行模型路由：简单任务使用轻量模型，复杂任务交给高端模型，确定性计算交给程序和专业算法。

资料核验提示： Qwen、DeepSeek 和 GLM 的版本、参数、上下文上限、许可证与 benchmark 会持续更新。发布或部署前，请查阅 Qwen 官方模型主页、DeepSeek 官方 GitHub 和 智谱开放平台 的最新模型卡与许可证说明。
