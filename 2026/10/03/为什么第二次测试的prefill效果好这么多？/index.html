为什么第二次测试的prefill效果好这么多？

发表于2026-10-03|更新于2026-10-03|人工智能
|总字数:2.4k|阅读时长:8分钟|浏览量:

为什么第二次测试的prefill效果好这么多？

最近在昇腾 A3 上测试 Qwen3.8-27B-W8A8 时，遇到了一个很典型、也很容易误判的现象：相同长度的请求，第一次测试的 Prefill 很慢，第二次却快了很多。

表面上看，第二次测试像是模型性能突然提升了 40 倍。但把 Prefill 和 Decode 拆开之后，会发现真正发生变化的主要是首 Token 延迟，Decode 性能几乎没有变化。

这也是大模型推理性能分析中一个很重要的经验：不要只看端到端耗时，要把 TTFT、TPOT 和 ITL 分开看。

一、两次 Benchmark 数据对比

两次测试的输入 Token 和输出 Token 完全相同：输入约 10 万 Token，输出 64 Token。

指标 第一次测试 第二次测试 变化
输入 Token 100054 100054 相同
输出 Token 64 64 相同
Benchmark 总耗时 27.30 s 2.19 s 约降低 12.5 倍
TTFT 25716.66 ms 638.43 ms 约降低 40.3 倍
TPOT 25.15 ms 24.61 ms 基本一致
ITL 24.75 ms 24.61 ms 基本一致
输出吞吐 2.34 tok/s 29.23 tok/s 约提升 12.5 倍
总 Token 吞吐 3667.15 tok/s 45732.38 tok/s 约提升 12.5 倍

最值得关注的是两组数据：

  • Prefill 相关的 TTFT 从 25.72 秒下降到 0.64 秒；
  • Decode 相关的 TPOT 始终保持在约 25 毫秒。

因此，问题不太像是模型的 Decode 算子突然变快，而更像是第二次请求没有完整重复执行 10 万 Token 的 Prefill。

二、TTFT、TPOT 和 ITL 分别说明什么？

1. TTFT：从请求到第一个 Token

TTFT（Time To First Token）表示从服务端收到请求，到返回第一个输出 Token 所经历的时间。对于一个长输入请求，TTFT 通常包含：

  1. 请求排队和调度；
  2. Prompt 的 Token 化与输入处理；
  3. Prefill 阶段的模型计算；
  4. KV Cache 的生成或读取；
  5. 第一个 Token 的采样与返回。

输入达到 100K Token 时，Prefill 往往是 TTFT 的主要组成部分。因此第一次 TTFT 达到 25.7 秒并不奇怪，真正需要解释的是第二次为什么只剩下 638 毫秒。

2. TPOT：生成阶段的平均耗时

TPOT（Time Per Output Token）通常用于观察 Decode 阶段的生成效率。两次测试分别是 25.15 ms 和 24.61 ms，差异很小，说明：

  • 模型权重和量化配置没有发生明显变化；
  • Decode 阶段的算力、带宽和调度状态基本稳定；
  • 第二次测试的整体加速，主要不是来自 Decode。

3. ITL：相邻 Token 的间隔

ITL（Inter-Token Latency）也基本一致，进一步说明两次请求在逐 Token 生成阶段的表现相近。

三、最值得优先排查的原因：前缀缓存

首要怀疑对象是 vLLM 的 APC（Automatic Prefix Caching，自动前缀缓存）。

正常情况下，模型收到 100K Token 的输入后，需要执行完整 Prefill，为这些输入 Token 计算并保存 KV Cache，然后进入 Decode 阶段生成 64 个 Token。

如果第二次请求的 Prompt 前缀与第一次完全一致，并且对应的缓存仍然有效，那么服务可以复用第一次请求已经计算出的 KV Cache。第二次请求只需要处理没有命中的部分，甚至可能几乎直接进入 Decode。

这里的 --dataset-name random 是一个非常重要的变量：两次独立运行是否生成了完全相同的随机 Prompt？

如果每次运行生成的 Token 序列不同，那么前缀缓存通常无法命中，APC 就不能单独解释第二次 TTFT 只有 638 毫秒。此时还需要重点考虑首轮编译、运行时初始化和内存预热等因素。

因此，验证 APC 时不能只比较输入长度，还要比较实际输入内容，至少确认：

  • 两次请求的 Token 序列是否完全一致；
  • tokenizer、chat template 和特殊 Token 是否一致；
  • 请求是否经过了会改变 Prompt 的随机处理；
  • 服务进程中间是否重启，缓存是否被清空。

输入长度相同，不等于前缀相同。 这是本次分析里最容易忽略的一点。

五、除了 APC，还有哪些首轮开销？

如果确认两次输入不同，或者关闭 APC 后差异仍然存在，可以继续排查以下因素。

可能原因 具体表现 当前优先级
APC 前缀缓存 第二次复用已经计算好的 KV Cache 很高，但需要确认 Prompt 一致
算子编译 Triton、PTO 或后端算子首次编译、加载 中
图编译 首次执行时构建计算图或编译执行图 中
设备运行时初始化 NPU Runtime、通信库或执行上下文首次初始化 中
内存分配与内存池预热 首次申请大块内存，后续复用内存池 中
输入处理差异 Tokenizer、模板或请求路径不一致 中
NPU 频率和温度变化 设备进入稳定工作状态后性能变化 较低

需要特别注意的是，首轮算子编译通常会影响某些算子的第一次执行，但 25.7 秒与 0.64 秒之间的差距非常大。对于 100K Token 输入，APC 或其他形式的 Prefill 复用仍然是最值得优先验证的方向。

六、如何设计一个可复现的验证实验？

实验一：关闭前缀缓存

在服务启动参数中显式关闭 APC：

然后按照下面的顺序测试：

  1. 关闭当前 vLLM 服务；
  2. 使用关闭 APC 的参数重新启动模型服务；
  3. 执行第一次 100K Token 请求；
  4. 不重启服务，立即执行第二次请求；
  5. 对比两次 TTFT、TPOT 和 ITL。

如果关闭 APC 后两次 TTFT 仍然接近，之前的差异就更可能来自缓存命中。如果差异依旧很大，则需要继续排查编译和运行时初始化。

注意，重启 benchmark 客户端不会清除服务端的 KV Cache；重启 vLLM 服务才会清除进程内缓存以及相关运行时状态。

实验二：固定 Prompt，而不是只固定长度

不要依赖每次独立运行的随机输入。可以保存一份固定的 Token 序列或固定文本，让两次请求使用完全相同的输入，再观察：

  • 第一次请求是否明显更慢；
  • 第二次请求是否明显变快；
  • 修改 Prompt 的最后一小段后，缓存命中范围如何变化；
  • 重启服务后，第二次请求是否重新变慢。

这个实验可以把“缓存是否命中”与“首轮运行时初始化”区分开。

实验三：查看服务日志和监控指标

关注 vLLM 版本对应的日志或 Prometheus 指标，重点寻找：

  • Prefix Cache Queries；
  • Prefix Cache Hits；
  • Prefix Cache Hit Rate；
  • KV Cache Usage；
  • Prefill Token 数量和 Prefill 耗时。

不同版本的指标名称可能不同，应以当前 vLLM 和 vLLM-Ascend 版本的实际输出为准。最好同时保存服务启动参数、模型版本、驱动版本、固件版本和设备信息。

七、为什么不能直接说“性能提升了 40 倍”？

40 倍这个数字来自 TTFT 的比值：

$$
\frac{25716.66}{638.43} \approx 40.27
$$

它只能说明这两次测试的首 Token 延迟相差约 40 倍，不能说明模型的通用 Prefill 算力提升了 40 倍。

原因有三个：

  1. 第二次可能复用了缓存，实际计算量已经不同；
  2. 测试只有 1 个请求，无法反映并发场景；
  3. 首轮编译、内存预热和设备初始化都可能让两次运行不处于同一状态。

更准确的说法应该是：

在当前测试条件下，第二次请求的 TTFT 比第一次低约 40 倍；但这更可能反映缓存或首轮开销的差异，而不是模型底层 Prefill 吞吐能力提升了 40 倍。

八、最终结论

这两次 Benchmark 的核心结论可以概括为：

  • 总耗时从 27.30 秒降到 2.19 秒，主要由 TTFT 下降造成；
  • TPOT 和 ITL 基本不变，说明 Decode 性能没有明显变化；
  • APC 是最值得优先验证的原因，但前提是两次请求的 Prompt 前缀确实相同；
  • 由于测试使用了 random 数据集，必须先确认两次实际输入是否一致；
  • 如果输入不同，应重点排查算子编译、图编译、运行时初始化和内存池预热；
  • 性能测试必须记录服务状态，并区分冷启动、热身后和缓存命中三种场景。

所以，第二次测试的 Prefill “好这么多”，最可能不是模型突然变强了，而是第二次测试执行的工作量已经和第一次不同。只有把缓存、编译和运行时状态控制住，才能得到真正可比较的 Prefill 性能数据。
